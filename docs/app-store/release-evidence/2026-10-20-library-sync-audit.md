Metadata identity is **GameID only** for favorites/recent/counters; new custom title/cover/tag shards use the app model's GameID/disc/revision identity or a supplied SHA-256 content identity for homebrew. Revisions/discs with the same ID intentionally share these fields today. Nearby catalog identity is stronger (`id:<GameID>|d<disc>|r<revision>`), while Provenance cloud ROM identity is an uppercase file MD5. None of these is a demonstrated universal metadata identity contract.

## Existing off-LAN reuse candidate (read-only research)

Provenance has a real ROM provider in `PVLibrary/Sources/PVLibrary/Cloud Sync/iCloud/CloudKit/CloudKitRomsSyncer.swift` and a schema in adjacent `CloudKitSchema.swift`. Its actual database is `CKContainer(...).privateCloudDatabase` (despite a stale schema comment saying public), with default-zone `ROM` records named `rom_<MD5>`. The primary container normally is `iCloud.org.provenance-emu.provenance`; Info.plist can override it and DEBUG defaults to `iCloud.org.provenance-emu.provenance.dev`. Release fallback to the dev container is read-only and may be inaccessible. Source iCube AppStore/NJB entitlements already list the Provenance production container; actual distribution-signed access requires verification.

Existing fields include `md5`, `systemIdentifier`, `fileData` CKAsset, `isArchive`, `originalFilename`, `relatedFilenames`, `relativePath`, `isDeleted`, title/statistics and custom-art asset. The record ID generator does not normalize by itself; callers uppercase MD5.

A bounded first adapter could query only GC/Wii metadata, show remote entries, download assets into contained staging, verify the full-ROM digest, and register complete files using iCube's existing importer. Keep it read-only initially: treat remote deleted records as unavailable sources, preserve acquired local copies, ignore Provenance path strings as destination authority, and do not write favorites/counters/art back until ownership/merge rules are agreed. Existing Nearby client/puller remains the resumable LAN path; durable subscription selection, deduplication by content, retry/cancel, quota/disk failures, boot ownership and cache-purge recovery are still required for automatic operation.

**Future off-LAN large-ROM limitation (not current release blocker):** Provenance upload currently hard-rejects a primary file above **500 MiB** (`CloudKitRomsSyncer.swift`, upload section around lines 905–917). Many GameCube/Wii images exceed this application cap. Thus a consumer of the existing schema alone cannot satisfy complete off-LAN GC/Wii mirroring. The current foreground-nearby release design can retain existing Range/SHA-256 transport and avoids this CloudKit cap. Reusing an external content server/WebDAV source can move large ROMs if the source is configured; a universal CloudKit solution needs a separately reviewed chunked manifest/assets contract (or verified alternative) and a Provenance writer change. No backend/schema/Provenance edits were made here.

## Bounded metadata retention and local recovery

The previous production store retained parsed JSON (including base64 cover strings) and decoded Draft covers for every game ever read. Title/tag getters requested Draft, so sorting/searching also populated both caches. A pre-change native production binary read titles for 32 games with 256 KiB covers and retained **11,184,896 encoded bytes + 8,388,608 decoded bytes = 19,573,504 cover payload bytes**. This excludes dictionary/string overhead and UIKit image caches; it is retained payload accounting, not an RSS measurement. Extrapolating the same graph to 1,000 covers gives 611,672,000 bytes (about 583 MiB). [Captured pre-change result](2026-10-20-native/library-metadata-retention-baseline.log). The archived Mirror-based proof depends on the pre-change private cache layout.

`LibraryMetadataStore` now retains a single LRU of full validated raw records plus optional lazily decoded Drafts, limited to **16 MiB accounted bytes and 64 records**. Accounting includes raw bytes, decoded cover bytes, title/tag/identity UTF-8 estimates and fixed per-entry overhead. It does not claim an exact process-heap ceiling; temporary JSON parsing/merge allocations and caller-owned Drafts are separate. A separate bounded **4 MiB / 8,192-entry summary LRU** retains only titles/tags after full-record eviction, avoiding repeated cover-shard reads/snapshots for sorting/searching. Its byte total is tracked incrementally; only actual eviction sorts its recency entries. Reload invalidates both cache owners. Only compact shard-name receipts remain per previously observed nonempty identity. `summary(for:)` returns title/tags without decoding covers: validation checks base64 alphabet, padding and exact decoded length without allocating decoded Data. Summary hits also touch any resident full record, preserving its LRU age without I/O. Existing full Draft reads continue to share immutable cover storage while resident. All mutable state, reads and writers use the serialized shared document gate; the Store is explicitly `@unchecked Sendable` under that gate contract.

Before evicting a nonempty full record, the store atomically writes a validated full recovery snapshot to **`Profiles/LibraryMetadataRecovery/<hash>.json`**. It merges cached bytes, the latest valid primary shard and an existing valid snapshot using opaque per-record timestamps and canonical-byte tie breaks, retaining clear tombstones and unknown records. This prevents an older store instance from replacing newer recovery data after a primary purge. Every required victim snapshot finishes before any victim leaves memory. Save preflights this recovery work before changing primary bytes; recovery/primary write failure leaves the previous authoritative cache intact. No lock spans network work. Canceled editor Drafts are never snapshot sources.

Missing primary shards recover resident/recovery data; malformed primary bytes remain untouched and the refresh reports an error once before serving a prior validated cached/snapshotted projection. If both copies of a known evicted shard disappear in the same session, full-record reads/commits report unavailable instead of interpreting the absence as clear; a previously cached lightweight title/tag summary can still be shown after reporting a failed refresh. A complete loss of both primary and recovery storage before a new process starts is unrecoverable without cloud/backup. Recovery snapshots duplicate durable local data on disk and remain subject to filesystem availability; failed snapshots are surfaced through the store API and preserve resident records. No extra cloud prefix or package release was introduced.
