# Cross-app custom library edits: proposed convergence contract

October 20, 2026. **Proposal only.** No counterpart, protocol, CloudKit database or metadata settings were changed by this research. Cross-app title/cover/tag convergence remains a release blocker. Nearby ROM mirroring while both apps are open is a separate requirement and does not imply permission to overwrite another app's library edits.

## Observed implementation

- iCube now owns `Profiles/LibraryMetadata/<SHA256(identity.rawValue)>.json`. Each title/cover/tags field is a separate opaque `{updatedAt, value}` record; `null` is a retained clear. The reviewed PVSyncRules 1.0.2 classifies only this canonical namespace as the existing `gameProfile` document bucket, with a 1 MiB shard cap. Covers are embedded bounded bytes, not paths; app validation also checks the shard/identity binding. The existing keyed timestamp merger can carry these records without a new CloudKit record type.
- iCube uses private container `iCloud.com.joemattiello.iCube`, zone `iCubeUserData`, record type `iCubeUserFile`. Provenance's AppStore entitlement source lists this sibling container, but its actual production-signed access and account convergence still need evidence.
- Provenance Realm `PVLibrary/Sources/PVRealm/RealmPlatform/Entities/PVGame.swift` and SwiftData `PVLibrary/Sources/PVLibrary/SwiftData/Game_Data.swift` store `title` directly. There is no independent custom-title value or classification-tags field. `genres` is catalog metadata; `RomDatabase.hideGame` even uses it for `hidden`. **Do not reuse genres for classification tags.**
- Provenance custom art is `customArtworkURL`, normally a PVMediaCache key, plus the `ROM.customArtworkAsset` CloudKit asset. This key is not transferable artwork data. `originalArtworkURL` is a separate fallback.
- Provenance `CloudKitRomsSyncer` uses its own private Provenance container, default-zone `ROM` records keyed `rom_<MD5>`. It has whole-record title/artwork fields and no compatible per-field clear/timestamp/tag contract. Its `updatePVGame` currently assigns title and customArtworkURL from cloud (around lines 2395/2417). Blindly projecting shared edits into those fields would let this independent writer overwrite them.
- Nearby `PVLibrarySharing` models `SharedGame` and `RemoteLibraryItem` carry display title, art presence/key and identity hints, but no edit stamps, clear records or tags. `ICubeDialectServer.entries()` passes nil disc/revision and derives an optional disc ID from best-effort `romSerial`. The current manifest/receiver is intentionally ROM-only. Catalog display values and an artwork GET are not a bidirectional edit contract.

## Smallest safe common data contract

Reuse the iCube shard document rather than mapping its fields onto Provenance's legacy ROM record. Extract the existing pure identity/codec/validation/store into a shared **product in the existing PVCloudSync repository**, for example `PVLibraryMetadata`. Keep it independent of UIKit, Realm and CloudKit. Both apps use the same implementation and tests; do not maintain two copied encoders or date-normalization rules.

1. Retain existing canonical identities: verified disc GameID + disc number + revision; SHA-256 content identity for homebrew/unidentified files. Never infer revision/disc zero from absent Provenance metadata, and never equate an MD5 with a SHA-256 or GameID. Filenames, product-code serials and library titles are not identity evidence.
2. Provenance keeps a local binding from its stable MD5 primary key to the verified shared identity and a full stat-bound receipt for the file inspected. Obtain disc identity through a bounded read-only Dolphin metadata bridge using the same DiscIO reader as iCube (including compressed formats). An authenticated transfer's verified SHA-256 and identity may be retained as a receipt, but a catalog's best-effort serial alone cannot create a binding. Missing/unverified identity stays visibly pending; it cannot edit a guessed sibling record.
3. Reuse the existing field limits: title 200 characters; up to 32 normalized tags of 40 characters; cover at most 256 KiB; shard at most 1 MiB. Covers use the shared bounded decoder/normalization before presentation and export. Preserve unknown records/fields. Validate known fields, identity binding and size before writing.
4. Preserve sparse field timestamps and null clears. Editing one field does not restamp another. Same-field ties use the existing deterministic canonical-byte ordering; a local subsequent edit raises its timestamp above the latest stored stamp. A clear means “remove the shared override and use this app's default,” not “delete the game” or “delete every cache.” Different metadata providers can have different default titles/covers after a clear.
5. Apply metadata only after identity verification; stage unknown-game edits until the corresponding game is imported/matched. Failed writes preserve prior bytes and visible projection. Store mutation/merge/commit shares a short file lock, never a network await. Reload publishes the app's actual observed library snapshots and invalidates search, sort and artwork caches.

## Transport comparison and recommendation

| Choice | Scope it actually solves | Required work and risk |
|---|---|---|
| **Existing private iCube zone, explicit same-account opt-in** | iCube ↔ Provenance on the same device or different devices using the same iCloud account; automatic metadata convergence independent of the ROM transport | Small metadata-only adapter in Provenance plus the shared codec/product and identity/projection work. No new CloudKit record type/zone. Must verify both apps' distribution entitlements, Production access and account transitions. Does not serve different accounts. |
| **Authenticated nearby edit envelope, per-peer opt-in** | iCube ↔ Provenance on different accounts/devices while both apps are open and reachable | Additive capabilities/routes/models in PVContinuity and PVLibrarySharing, explicit edit-sync grants, digest/version-driven polling and authenticated read/merge/write semantics. Existing ROM read grants do not authorize metadata writes. Both servers and clients change; cannot be completed by adding a JSON field to only one client. |
| Existing catalog title/artwork, or writing Provenance ROM cloud fields directly | Display previews / one-way legacy record updates | Insufficient: no field clears, tags, concurrency contract or identity parity; retain these paths for their existing purposes. |

**Recommended first implementation:** explicit opt-in same-account adapter using the existing iCube zone. This is the smallest code and protocol change that provides actual bidirectional convergence. Add a clear setting such as “Share custom library edits with iCube” in Provenance and expose its scope/status in iCube; do not silently enable it under general ROM sharing. Its local root is a dedicated app-owned metadata store, not the ROM directory.

The adapter uses existing `CloudKitSyncProvider` and generic document merger, but filters **every local/remote operation to canonical metadata shards**. It does not scan, download, upload or delete iCube saves, firmware or INIs. **Never call the provider's whole-zone purge from Provenance's metadata controls**: that zone also contains iCube progress. Turning sharing off retains data. Field reset writes a clear record. Account change invalidates account-specific index/choices and stale workers before publishing new data.

Same-account CloudKit authorization is distinct from nearby `ic` automatic-trust hashing; it does not require declaring an unapproved shared salt. Conversely, a nearby peer cannot be assumed to share an iCloud account merely because both binaries hold a container entitlement.

**If different-account edit convergence is required at launch**, the second transport is also required; the same-account adapter cannot close that row. Preserve Bonjour service identity and catalog/manifest v1. Negotiate an additive `libraryEditsV1` capability, then use a separate authenticated bounded edit endpoint keyed by verified game identity/content evidence. A peer must grant explicit metadata synchronization; revoke cancels work and pending writes. Use the same field envelope/clear semantics. No metadata path is added to the existing ROM file manifest, and no arbitrary file path is accepted from the sender. A per-shard revision/digest changes when edit bytes change; the current catalog version hash of key/ROM size cannot detect an edit.

## Provenance projection and migration boundary

Keep the shared sidecar authoritative and legacy OpenVGDB/ROM fields as app defaults. A minimal first counterpart can avoid a Realm schema migration by projecting shared title/cover/tags into immutable render/search models, using a local MD5↔shared-identity index. However, **all** title/artwork/search/sort/details/share readers must use that projection before acceptance; simply changing one SwiftUI card is insufficient.

Principal existing integration points:

- `PVUI/Sources/PVSwiftUI/Consoles/GameCellModel.swift`: currently snapshots `g.title` and `g.trueArtworkURL`; add the shared projection and classification tags.
- `PVUI/Sources/PVSwiftUI/Consoles/ConsoleGamesViewModel.swift`: cached search currently checks only model title; include tags and invalidate cached results on shared metadata publication.
- `PVUI/Sources/PVUIBase/SwiftUI/GameItem/GameItemPresentable.swift` and `PVGame+GameItemPresentable.swift`: legacy PVGame conformity reads its stored title; route through an effective metadata snapshot or explicit display properties. Audit details, UIKit, tvOS, list sorting and export labels as part of this step.
- `PVUI/Sources/PVSwiftUI/Consoles/ConsoleGamesView+GameContextMenuDelegate.swift` and `PVLibrary/.../Database/Realm Database/RomDatabase.swift:renameGame`: explicit rename/artwork edits must write the shared fields when opted in. Commit sidecar data before reporting success; keep cancellation and failed writes transactional.
- `PVUI/Sources/PVSwiftUI/Settings/Views/NearbyLibraries/LibrarySharingService.swift`: served snapshots currently read raw Realm title/artwork; use the same effective projection so previews match the local UI.
- `PVLibrary/.../Cloud Sync/iCloud/CloudKit/CloudKitRomsSyncer.swift`: legacy cloud updates must remain fallback updates and must not erase the shared sidecar. Do not export an effective shared value as a fresh user edit when applying a legacy cloud record; that creates a sync loop.

Legacy title migration needs an explicit rule: historical Provenance rename writes directly into `title`, and its customization mask is not reliably set by the inspected rename path. Do not restamp every imported catalog title as a user override. Default to sharing new explicit edits; offer user-confirmed adoption of existing custom title/artwork, filling only absent shared fields without replacing newer stamped fields. Artwork adoption exports bounded image bytes, never PVMediaCache keys. Old/default title recovery after a clear must be stated accurately; the historical original may no longer be stored.

If complete projection coverage cannot be achieved safely, use additive Realm/SwiftData custom-override/index fields with a reviewed migration instead. That costs more upfront but is safer than repeatedly overwriting `PVGame.title` and trying to race every existing metadata/cloud writer. This is a counterpart implementation decision that must be resolved before coding, not an excuse to treat the current bridge as complete.

## Concrete implementation sequence and tests

1. **Freeze shared contract/product.** PVCloudSync `Package.swift`, new `Sources/PVLibraryMetadata/` and tests: extract identity, canonical codec, normalization, file transaction and validation from iCube `LibraryMetadataStore`; retain package classifier 1.0.2 namespace. Test golden byte fixtures in both clients, unknown fields, null clears, all merge algebra properties, bounds/identity mismatch and failed atomic writes. No CloudKit schema deployment is needed for this reuse.
2. **Verify identity bridge.** New Provenance `PVLibrary/.../EcosystemIntegration/LibraryMetadataIdentityResolver.swift` plus a read-only PVDolphinCore metadata API if no existing public reader supplies the tuple. Tests: ISO/GCM and compressed RVZ fixtures, disc 1/2, revisions, same content in different paths, same-name different homebrew, patch variants and missing/remote-only files. Do not guess when evidence is absent. Patch/base aliasing policy must match iCube's approved rule.
3. **Add Provenance metadata-only store/cloud adapter.** New `LibraryMetadataSyncCoordinator` under PVLibrary cloud sync, existing provider configuration, account-bound index and exact shard filter. Integrate lifecycle and emulation deferral using Provenance's existing pause-for-emulation policy. Test old-account delayed completion, offline edits on both sides, first-download concurrent local creation, merge failure, signed out/quota errors, disabled/re-enabled sync, and tvOS purge with surviving/missing index. Assert attempts to touch non-metadata paths/whole-zone purge are impossible.
4. **Add explicit settings and edit/projection adapters.** Modify the principal UI/model files above, with Realm/SwiftData migration only if selected. Tests: Save/Cancel/read failure/failed write, title/cover/tag clear, concurrent unrelated edits, legacy ROM cloud update after shared edit, real search/sort/details/nearby-preview refresh, restart and cache loss. Verify no sidecar data leaks into games/settings or other accounts.
5. **Optional different-account nearby transport.** PVContinuity library provider/server/client model/protocol files; Provenance `PVLibrarySharing/Server/Host/SharedLibrary.swift`, `Server/Dialects/ICubeDialectServer.swift`, `Sources/ICubeContinuitySource.swift`, `Sources/ContinuityWire.swift`; both app adapters. Contract tests pair both directions, old peers with no capability, missing grant, revoked grant mid-transfer, corrupt/oversized payload, replay/version conflicts and no metadata writes from a ROM-only grant. Include per-shard digest refresh without ROM changes.
6. **Distribution/device acceptance.** iPhone↔iPad↔Apple TV, same-device apps, same-account Production convergence and (if selected) different-account foreground nearby convergence. Record exact builds and signed entitlements. Current source/native evidence does not close these gates.

No implementation, dependency publication or counterpart edit was performed for this proposal.
